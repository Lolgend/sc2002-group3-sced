4. Understanding whether an unused Random parameter affects substitutability

INPUT:
The parent chooseMenuItem() method uses random, but the Critic chooses the cheapest item without using it. Does this difference conflict with the Liskov Substitution Principle (LSP)?

OUTPUT:
The important distinction is between not using a parameter and not satisfying the parent method's contract.

CriticCustomer still declares chooseMenuItem(Menu menu, Random random). It retains the parameter so that its method matches and overrides the parent method. The waiter can therefore continue making the same call through a Customer reference.

The Critic's implementation follows a different selection rule, but it still returns a menu item through the same method interface. In this design, different customer preferences are an intended variation. Not using the random generator does not, by itself, violate the Liskov Substitution Principle (LSP).

Removing the Random parameter would be a different issue. That would create a method with a different signature rather than override the existing two-parameter method. The waiter's existing call would not dispatch to that new method.

Matching the signature enables overriding, but LSP also concerns behaviour: the subclass must remain usable under the expectations established for Customer. Here, the fixed cheapest-item preference is compatible with the intended customer-selection variation.

INPUT:
Then why is our game reproducible? Is it because we use a seed?

OUTPUT:
Yes. Restaurant creates the random generator using the configured seed, and GameConfig supplies the default seed 42L.

A seeded Random produces a repeatable sequence. Starting again with the same configuration, manager inputs and order of random calls therefore reproduces the same selections.

The fixed seed does not mean every customer orders the same dish. It means the sequence can be repeated. Different manager actions or a different order of random calls can still produce different results.

The Critic's cheapest-item selection is deterministic independently of the random generator. It keeps the parameter for method compatibility but does not consume a random value when selecting an item.

5. Comparing a setup change with extension through inheritance

INPUT:
This is an OODP project. Saying that Stage 1 is no longer needed does not seem like enough reason to modify its code. If we can change earlier code freely in Stage 2, how does that demonstrate evolution and extensibility?

OUTPUT:
Keeping a Stage 1 tag preserves a historical version, but it does not demonstrate that the design is extensible. The reason for modifying the creation method should be based on responsibilities and the scope of the change.

In this implementation, several variations already use extension points:

- VIP and Critic waiting penalties override the existing penalty method while reusing the parent's decay process.
- The Critic overrides chooseMenuItem(), while the waiter continues calling through Customer.
- VIP billing uses the new customer-side pricing method. This required adding an extension point and changing the waiter's price lookup, so it should be described as design evolution rather than something Stage 1 already supported completely.

For arrivals, both approaches have a design rationale.

Updating Restaurant.createCustomer() directly confines the change to the setup that determines which customer objects enter the game. Arrival timing, ID allocation, queue insertion and the shared service flow remain reusable. Manual §4.4 anticipates small registration or setup changes.

Adding MixedCustomerRestaurant would use the existing protected createCustomer() method as an inheritance extension point. The subclass could override customer creation while leaving Restaurant unchanged. This demonstrates extension through overriding, but it adds another restaurant class for the fixed arrival arrangement.

The direct update is therefore reasonable because the creation setup changes locally while stable business behaviour is reused. “Stage 1 is no longer needed” is not the design justification.

9. Deciding which getters help explain the diagrams

INPUT:
You seem to have retained some getters. Can you explain why?

OUTPUT:
The decision should depend on what a method communicates, rather than whether its name begins with get.

Some getter-style methods express polymorphic rules. For example, getWaitingSatisfactionLoss() and getCustomerType() have different implementations in the customer subclasses, so showing them helps explain the variation between customer types.

Others calculate or locate something rather than simply return a field. Examples include getServedCustomersCount(), getAveragePaidSatisfaction() and getLowestNumberedFreeTable().

Collection accessors such as getOrders(), getCustomers() and getArrivalTurns() can help explain encapsulation when they return an unmodifiable view or a defensive copy. However, these accessors can still be omitted from the class diagram if they make it too crowded and the relevant design information is already clear.

The sequence diagram has a different purpose. A getter may be useful there because its returned value explains a specific interaction:

- getSatisfactionAtPayment() identifies the satisfaction snapshot used in the final statistics.
- getFinalPriceCents() shows that payment uses the price already locked in the order.
- getWaitingSatisfactionLoss() shows how the VIP waiting penalty is obtained through polymorphism.

A class diagram can omit routine accessors while a sequence diagram still shows accessor calls that matter to the selected scenario.
